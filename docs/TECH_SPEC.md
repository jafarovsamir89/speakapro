# SpeakAPro — техническое задание

Версия документа: **0.1**  
Статус: **MVP specification**

## 1. Назначение

SpeakAPro — Android-приложение синхронного голосового перевода окружающей речи.

Пользователь должен иметь возможность надеть наушники, запустить режим прослушивания и слышать перевод речи окружающих максимально близко к реальному времени.

Основной продуктовый сценарий MVP:

> Пользователь находится в другой стране, не понимает язык окружающих, запускает SpeakAPro и слышит перевод их речи в наушниках без необходимости вручную записывать отдельные фразы.

## 2. Главная цель MVP

Доказать, что связка Android + Gemini Live Translation обеспечивает достаточно комфортный непрерывный перевод для реального использования.

Для MVP приоритеты расположены в таком порядке:

1. стабильный аудиопоток;
2. минимально возможная end-to-end задержка;
3. корректное воспроизведение именно в наушники;
4. устойчивость WebSocket-сессии;
5. понятный интерфейс;
6. экономия трафика и стоимости.

Количество дополнительных функций не является приоритетом.

## 3. Целевая платформа

### MVP

- Android;
- Kotlin;
- Jetpack Compose.

### Позже

## 4. Основной режим: Listen Mode

### 4.1. Запуск

Пользователь:

1. запускает приложение;
2. разрешает доступ к микрофону;
3. подключает Bluetooth или проводные наушники;
4. выбирает целевой язык;
5. нажимает кнопку `Начать перевод`.

### 4.2. Во время работы

Приложение:

1. захватывает звук с микрофона телефона;
2. преобразует/получает поток в raw PCM 16-bit, 16 kHz, mono, little-endian;
3. формирует аудиочанки примерно по 100 ms;
4. передаёт их в Gemini Live Translation по WebSocket;
5. принимает переведённый аудиопоток;
6. воспроизводит raw PCM 16-bit, 24 kHz, mono в выбранное выходное аудиоустройство;
7. отображает входную транскрипцию;
8. отображает транскрипцию перевода;
9. показывает текущее состояние сессии.

### 4.3. Остановка

При нажатии `Остановить` приложение должно:

- прекратить запись микрофона;
- прекратить отправку аудио;
- остановить/доиграть допустимый хвост выходного буфера;
- закрыть WebSocket;
- остановить foreground service;
- освободить AudioRecord и AudioTrack;
- вернуть UI в состояние Idle.

## 5. Gemini Live Translation

### 5.1. Модель MVP

```text
gemini-3.5-live-translate-preview
```

Важно: модель имеет статус Preview, поэтому её идентификатор и API-контракт должны быть вынесены в конфигурацию, а не размазаны по приложению.

### 5.2. Session setup

Для translation session требуется:

- `responseModalities: ["AUDIO"]`;
- `inputAudioTranscription: {}`;
- `outputAudioTranscription: {}`;
- `translationConfig.targetLanguageCode`;
- `translationConfig.echoTargetLanguage`.

Для режима `Listen` по умолчанию:

```text
echoTargetLanguage = false
```

Это означает, что речь, уже произнесённая на целевом языке, не должна повторно озвучиваться как перевод.

### 5.3. Исходный язык

В MVP пользователь выбирает только **язык, на котором хочет слышать перевод**.

Не требуется обязательный ручной выбор исходного языка: Live Translation выполняет определение языка входной речи.

Позже можно добавить опциональный UX-фильтр/подсказку исходного языка, если это потребуется для качества или продуктовой логики.

### 5.4. Транскрипции

Нужно поддержать два независимых потока текста:

```text
input transcription  -> что сказал собеседник
output transcription -> что было переведено
```

UI не должен блокировать аудиопоток при обновлении текста.

## 6. Аудиоподсистема Android

### 6.1. Audio capture

Компонент: `AudioRecorder`.

Основа:

- Android `AudioRecord`;
- mono;
- PCM 16-bit;
- 16 kHz;
- отдельная coroutine/worker для чтения;
- никаких операций UI в realtime capture loop.

Нужно предусмотреть корректную обработку:

- отсутствия разрешения RECORD_AUDIO;
- ошибки инициализации AudioRecord;
- смены аудиоустройства;
- потери Bluetooth;
- остановки приложения;
- системного отзыва аудиофокуса.

### 6.2. Chunking

Базовый размер отправки:

```text
100 ms
```

При 16 kHz / 16-bit / mono это примерно:

```text
16,000 samples/sec × 0.1 sec × 2 bytes = 3,200 bytes
```

Это исходная точка. Реальную задержку и стабильность необходимо измерить на физических устройствах.

### 6.3. Playback

Компонент: `AudioPlayer`.

Основа:

- Android `AudioTrack`;
- streaming mode;
- PCM 16-bit;
- 24 kHz;
- mono;
- bounded playback queue.

Нельзя допускать бесконечного накопления выходных чанков. Если сеть/воспроизведение начинает существенно отставать, стратегия обработки очереди должна быть явно определена и измерена.

### 6.4. Audio routing

Компонент: `AudioRouter`.

MVP должен приоритетно выводить перевод в:

1. Bluetooth-наушники;
2. проводные/USB-наушники;
3. встроенный динамик — только как fallback или при явном разрешении UX.

Нужно отображать пользователю текущее выходное устройство.

Для режима Listen рекомендуется предупреждать пользователя, если наушники не подключены.

## 7. Network / WebSocket

Компонент: `GeminiLiveClient`.

Ответственность:

- открытие WebSocket;
- отправка setup message;
- ожидание подтверждения setup;
- отправка realtime audio;
- чтение server messages;
- декодирование base64 audio;
- публикация транскрипций;
- публикация состояния соединения;
- корректное закрытие;
- reconnect policy.

### 7.1. Состояния соединения

Минимальный state machine:

```text
Idle
  ↓
RequestingToken
  ↓
Connecting
  ↓
Ready
  ↓
Listening
  ↓
Stopping
  ↓
Idle
```

Ошибочные состояния:

```text
PermissionError
TokenError
NetworkError
GeminiError
AudioInputError
AudioOutputError
```

UI должен получать эти состояния через единый observable state.

### 7.2. Reconnect

При кратковременной потере сети:

- не зависать;
- прекратить запись/отправку либо безопасно остановить pipeline;
- показать состояние переподключения;
- выполнить ограниченное число попыток reconnect;
- не создавать одновременно несколько Live-сессий.

Точную политику retry определить после первых интеграционных тестов.

## 8. Безопасность API

### 8.1. Запрещено

Нельзя хранить production Gemini API key:

- в Kotlin source;
- в `BuildConfig` production APK;
- в `strings.xml`;
- в assets/resources;
- в remote-config значении, доступном без server-side контроля.

### 8.2. Production architecture

```text
Android app
    ↓ HTTPS
SpeakAPro backend
    ↓
Gemini Auth Token Service
    ↓
short-lived ephemeral token
    ↓
Android app
    ↓ direct WebSocket
Gemini Live API
```

Backend хранит постоянный Gemini API key.

Android получает короткоживущий ephemeral token и использует его для прямого WebSocket-соединения с Gemini.

Для Live Translation ephemeral tokens работают через `v1beta` constrained endpoint.

### 8.3. Development mode

Для самого первого локального прототипа допускается developer-only механизм подключения ключа, но:

- файл с ключом должен быть в `.gitignore`;
- ключ никогда не коммитится;
- такой путь не попадает в release build;
- до внешнего тестирования должен быть заменён backend token flow.

## 9. Foreground Service

Для продолжительного использования микрофона вне активного экрана необходим `TranslationService`.

Он должен:

- работать как foreground service соответствующего типа;
- показывать постоянное уведомление;
- отображать, что микрофон и перевод активны;
- иметь действие `Остановить`;
- синхронизировать состояние с UI;
- корректно завершаться после stop/error.

MVP сначала может быть отлажен при открытом Activity, затем foreground service добавляется до beta-тестирования.

### 10.1. Главный экран

Минимальный состав:

```text
SpeakAPro

Переводить на:
[ Русский ▼ ]

🎧 Наушники подключены

Original

```

### 10.2. UX требования

- mobile-first;
- крупная Start/Stop кнопка;
- минимум действий;
- основной экран не перегружать настройками;
- состояние микрофона и подключения всегда очевидно;
- текст оригинала визуально слабее перевода;
- экран не должен постоянно прыгать при частичных транскрипциях;
- поддержать dark/light system theme позднее, если это не мешает MVP.

## 11. State management

Один источник истины для основного экрана.

Пример логической модели:

```kotlin
TranslatorState(
    status,
    targetLanguage,
    inputTranscript,
    outputTranscript,
    audioOutputDevice,
    latencyMs,
    error
)
```

Конкретная реализация может использовать ViewModel + StateFlow.

## 12. Нефункциональные требования

### 12.1. Latency

Нужно измерять, а не угадывать.

Первоначальная продуктовая цель:

- воспринимаемый перевод должен начинаться как можно ближе к речи;
- отсутствие искусственной пакетной задержки на целые предложения;
- приложение не должно само добавлять секунды из-за больших локальных буферов.

В debug-режиме желательно иметь latency telemetry:

```text
capture timestamp
send timestamp
first translated audio received
first translated audio played
```

### 12.2. Stability

Сессия должна выдерживать длительное прослушивание без:

- утечек AudioRecord/AudioTrack;
- накопления памяти;
- бесконечного роста playback queue;
- создания дублирующихся WebSocket;
- зависания UI.

### 12.3. Privacy

По умолчанию:

- не сохранять raw audio;
- не создавать локальную историю без отдельного решения;
- явно показывать активный микрофон;
- сообщить пользователю, что аудио передаётся внешнему сервису для перевода;
- политика конфиденциальности должна отражать реальный data flow до публикации.

## 13. Оптимизация стоимости

Не оптимизировать преждевременно ценой качества.

После рабочего pipeline измерить:

- реальное число входных аудиотокенов;
- реальное число выходных аудиотокенов;
- длительность сессий;
- долю тишины;
- влияние client-side VAD;
- стоимость 5/15/30/60 минут реального использования.

Client-side VAD рассматривать только после baseline-теста непрерывной передачи, чтобы не обрезать начало/конец речи и не ухудшить перевод.

## 14. MVP acceptance criteria

MVP считается технически доказанным, если на физическом Android-устройстве выполняются все пункты:

- [ ] приложение получает разрешение микрофона;
- [ ] пользователь выбирает целевой язык;
- [ ] AudioRecord стабильно выдаёт PCM 16 kHz;
- [ ] приложение открывает Gemini Live Translation session;
- [ ] 100 ms chunks передаются без регулярных разрывов;
- [ ] Gemini возвращает input transcript;
- [ ] Gemini возвращает translated transcript;
- [ ] Gemini возвращает translated audio;
- [ ] AudioTrack непрерывно воспроизводит 24 kHz PCM;
- [ ] звук идёт в подключённые наушники;
- [ ] Start/Stop можно выполнить много раз без перезапуска приложения;
- [ ] потеря сети не приводит к зависанию;
- [ ] API key отсутствует в release APK;
- [ ] длительная сессия не показывает очевидного роста памяти/очереди;
- [ ] измерена реальная end-to-end latency.

## 15. После MVP

### Phase 2 — Conversation Mode

Двусторонний сценарий:

```text
Собеседник → телефон → перевод → наушники пользователя
Пользователь → push-to-talk → перевод → динамик телефона
```

Push-to-talk предпочтителен для первой двусторонней версии, потому что упрощает routing, echo control и определение направления разговора.

### Phase 3

- accounts;
- subscription;
- usage limits;
- analytics;
- history opt-in;
- offline fallback;
- iOS;
- улучшенное управление аудиоустройствами;
- адаптивный VAD;
- качество в шумной среде.

## 16. Технические риски

### Preview API

`gemini-3.5-live-translate-preview` может изменить контракт или быть заменён. Интеграция должна быть изолирована за `GeminiLiveClient`/adapter layer.

### Bluetooth latency

Bluetooth сам добавляет задержку. Нужно тестировать несколько гарнитур и не приписывать всю задержку модели.

### Noisy environment

Вокзалы, рестораны, улица, несколько говорящих людей и музыка — обязательные реальные тесты.

### Audio feedback

При использовании динамика телефона переведённый звук может снова попадать в микрофон. В Listen Mode основной сценарий — наушники.

### Multiple speakers

MVP не гарантирует speaker diarization. Главная задача — понятный перевод общего входного речевого потока.
